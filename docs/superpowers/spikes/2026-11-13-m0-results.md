## How it works (technique for the adapters)

**Fake connection.** `class FakeConnection : Connection(PacketFlow.SERVERBOUND)` sets `channel = EmbeddedChannel()`
(open, so `isConnected()` is true) and `address = InetSocketAddress("127.0.0.1", 0)`. It overrides
`send(Packet<*>, ChannelFutureListener?, boolean)` to drop everything; the 1- and 2-arg overloads delegate to it.

**Spawn (variant A).**
1. `ServerPlayer(MinecraftServer.getServer(), level, GameProfile(uuid, name), ClientInformation.createDefault())`.
   `level` is `(world as CraftWorld).handle`.
2. `ServerGamePacketListenerImpl(server, fakeConnection, bot, CommonListenerCookie.createInitial(profile, false))`. Its
   constructor sets `bot.connection`.
3. `bot.connection.handleAcceptPlayerLoad(ServerboundPlayerLoadedPacket())`. **Required:** until the "client loaded"
   flag is set, `ServerPlayer.isInvulnerableTo` returns true (`!connection.hasClientLoaded()`), so the bot would take
   no damage for 60 ticks. The call fires Paper's `PlayerClientLoadedWorldEvent`.
4. `bot.absSnapTo(x, y, z, yaw, pitch)`, then `level.addNewPlayer(bot)`. The bot is **not** passed to
   `PlayerList.placeNewPlayer`, so there is no join event or message and no playerdata load or save. The default
   game mode is survival.
5. Remove with `level.removePlayerImmediately(bot, Entity.RemovalReason.DISCARDED)`. The real adapter should also detach
   advancement triggers, which vanilla does in `PlayerList.remove`. The name differs per version, see below.

**Per-tick input application.** The level ticks the bot like any player (`ServerLevel` entity tick → `ServerPlayer.tick()`).
Real players get their physics from `ServerGamePacketListenerImpl.tickPlayer()` → `player.doTick()`, which is driven by
the network connection tick. A fake connection is never ticked, so `FakeBot` overrides `tick()`:
```
super.tick()                    // ServerPlayer.tick(): game mode, containers, advancements (no physics)
applyStoredInput()              // yRot/xRot/yHeadRot, zza=forward, xxa=strafe(+left), setJumping(jump),
                                // isSprinting, isShiftKeyDown, setLastClientInput(Input(f,b,l,r,jump,shift,sprint))
xo = x; yo = y; zo = z
doTick()                        // vanilla Player.tick() -> LivingEntity.aiStep() -> travel(): gravity, friction,
                                // collision, step-up, jumping, item-use timing, food
```
It does *not* do the real-player snap-back (`absSnapTo(firstGoodX…)`), because the server is the authority for bots.
On the server `Player.canSimulateMovement()` / `isEffectiveAi()` return true, so `travel()` runs. `LivingEntity.applyInput()` only
decays `xxa/zza` by 0.98, so inputs must be written every tick, before `doTick()`.

**Actions used:** `bot.attack(nmsEntity)` (Player.attack), `bot.getAttackStrengthScale(0.5f)`,
`bot.gameMode.useItem(bot, level, bot.getItemInHand(hand), hand)` (the same path as the use-item packet; it starts eating
or blocking), `bot.isBlocking`, `bot.isUsingItem`. Inventory, food, damage and potion effects go through the Bukkit
`CraftPlayer` (`bot.bukkitEntity`).

## NMS names used, and differences 1.21.11 → 26.2

`net.minecraft.world.entity.player.Input(7 booleans)`, `ServerGamePacketListenerImpl(server, conn, player, cookie)`,
`handleAcceptPlayerLoad(ServerboundPlayerLoadedPacket())`, `CommonListenerCookie.createInitial(profile, false)`,

Differences found while reading the sources (they did not affect the spike):
- `PlayerAdvancements.stopListening()` (1.21.11) was renamed to **`clearTriggers()`** (26.2). It is needed on bot removal.
- `LivingEntity.jumping` is `public` in 1.21.11 and `protected` in 26.2. Use `setJumping()`.
- `CommonListenerCookie` component `brandName` (1.21.11) was renamed to `clientBrand` (26.2). We only use `createInitial`.
- `ResourceLocation` → `Identifier` in 26.x (not used here).
- Paper's `InteractionResult.Success` `PaperSuccessContext` has different fields (`placedBlockPosition` vs
  `placedPos, updatedBlockEntity`). Only the toString differed.
- World folder layout (playerdata path) differs, see Q6.
- `ServerPlayer` in 1.21.11 has no `spawnInvulnerableTime`. Spawn protection is only the client-loaded flag (step 3).

## Other observations for later tasks

- **Bots load chunks like players.** A variant-A bot is registered with the chunk system through the level's
  `addNewPlayer`. `spike_flat` saved 1908 chunks after about 10 short-lived bots. Expect view-distance chunk loading per bot,
  and consider the scaling cost. Paper has per-player view-distance API, which could be used on the bot.
- `world.isAutoSave = false` was set on the test world. Player entities are never written to chunk entity storage
  in any case (`EntityType.PLAYER` is not serialisable).
- Hidden-in-tab technique (manual mode): when a real player joins, the spike sends
  `ClientboundPlayerInfoUpdatePacket(EnumSet.of(ADD_PLAYER, UPDATE_GAME_MODE), listOf(bot))` **without** `UPDATE_LISTED`.
  The client then knows the profile (needed to render the entity) but does not list it. This has not been verified with a client yet.
- No skin was set: `GameProfile(uuid, name)` has no textures, so the default skin is expected. Skins need a signed
  `textures` property on the profile (a later task).
- Benign log noise: on the first creation of a `WorldType.FLAT` world via `WorldCreator` without generator settings,
  1.21.11 logs `ERROR: No key layers in MapLike[{}]` and falls back to the default flat layers (bedrock/dirt/grass,
  ground Y −60). 26.2 printed `oshi` Windows perf-counter errors at startup, which are environmental.
- Dev servers run unattended: the plugin calls `Bukkit.shutdown()` after the checks. run-paper forwards stdin, so
  `(sleep 75; echo stop) | ./gradlew …` also stops a server cleanly.

## Performance (Task 13: `load:100` self-test)

Run with `./gradlew :plugin:selfTest -Pselftest=load:100` (1.21.11, Paper 1.21.11-132) and
`./gradlew :plugin:selfTest_26_2 -Pselftest=load:100` (26.2, Paper 26.2-135), 2026-11-16.
**These are dev-PC numbers, not a server:** a Windows 11 laptop (AMD Ryzen 7 260, 23 GB RAM), default run-paper JVM
flags, with the IDE and other programs running. Expect run-to-run noise of a few tenths of a millisecond; compare
before/after on the same machine only.

**What `load:N` does.** N/2 HARD trainers, each fighting its own dummy owner in its own arena, spread over three
flat worlds (`pvpbots_selftest`, `_2`, `_3`), plus the other N/2 as HARD ally squads of 10 (5 boss areas for N = 100).
Each boss area has a dummy player, three zombies that come back 20 ticks after they die, and one AI-less zombie on a
5-high pillar that the allies cannot walk up to, so they also path-check and use the bow. Dummies are fake players
that are not registered as bots (55 for N = 100), so they load and are sent chunks like real players. All sessions
start in the same tick (spawn burst). After 100 ticks (the 3 s countdown is over), 1200 ticks are measured.
*Bot work* is the wall time of `BotManager.tickBots` (all `BotController.tick` calls) per tick. *Server MSPT* comes
from Paper's `ServerTickEndEvent`; it includes the dummies, zombies, arrows and the self-test itself. **Pass: average bot work ≤ 10 ms/tick.**

**Spawn burst** (100 bots in one tick, artificial worst case; real spawns are spread out): `BotManager.spawn` takes
about 5.3–6.4 ms per bot, almost all of it in the adapter's `spawn` (`ServerPlayer` creation and adding it to the level;
the kit takes 0.2 ms, distances 0.01 ms). That tick took 822 ms before / 729 ms after on 1.21.11, and 665 / 682 ms on 26.2. The next 100 ticks
average 32–47 ms MSPT, most of it from the dummies' own chunk sending (about 2600 chunks). Bots no longer get chunks:
before the change they got about 5000 in those 100 ticks, after it 0.

**What was changed and why:**
1. **Ally reachability check throttled (the hot spot).** `reachableOnFoot` (A*) ran on every target refresh, which
   is every 3 ticks at HARD. For a target that cannot be reached, A* explores the whole area (about 0.7 ms each).
   Now `ReachCheck` (pure, unit-tested) runs it only when the target changes, the bot or the target moves more than
   2 blocks, or 20 ticks have passed. A path it finds becomes the bot's current path, so `nextWaypoint` no longer
   searches the same route again (suspect: A* twice per refresh).
2. **Staggered target refresh.** `RefreshClock` (pure, unit-tested) backdates a bot's first refresh by a random
   0..period−1 ticks, so bots spawned in the same tick do not all refresh in the same tick.
3. **No chunk sending to bots.** `isRealPlayer = true` is needed for chunk loading/ticking around bots, but it also
   made Paper build a chunk packet for each bot (about 50 per bot at spawn, then about 5–7 per tick across all bots
   while they move). Bots now get `Player#setSendViewDistance(0)` (Paper API, set in `BotManager.applyDistances` on all
   versions; no adapter change). Paper's send radius 0 sends no chunks at all, while the load/tick distances stay 2.
   Effect on steady MSPT: about −0.5 ms (1.21.11: 11.95 → 11.43 with only this change toggled). The default
   self-test still passes on 1.21.11, 26.1 and 26.2 (A1 zombies near the allies still move and die).

**Measured but not changed:** the hostile scan costs 0.15–0.22 ms/tick for 17 scans, so a shared per-area cache
is not needed. `Ballistics.pitchFor` (inside the brain phase) costs 0.07 ms/tick. A per-search block-read cache in
`BukkitBlockGrid` was tried: reachability went from 2.24 to 2.04 ms, within noise, so it was reverted.

**Remaining:** p95 bot work is about 14 ms. A tick goes over 10 ms when several allies re-check a target they
cannot reach at the same time, for example right after the pillar zombie respawns. The budget (average) is met with
a wide margin. Adapter spawn costs about 5–8 ms per bot, so mass spawns in one tick stalled the server; this is now
rate-limited (next section).

### Spawn rate limit (final review, ruling R11: `bot.spawns-per-tick`, default 2)

Since the final-review fixes, events never spawn bots directly: a granted spawn waits in a FIFO queue (its slot
reserved) and the director spawns at most `bot.spawns-per-tick` bots per server tick. Same `load:100` runs, same
laptop, 2026-11-16 (1.21.11 Paper on Java 25; 26.2):

| 100 bots, spawns-per-tick 2 | 1.21.11 | 26.2 |
|---|---|---|
| Bot work ms/tick (steady, 1200 ticks): avg / p95 / max | **3.57** / 13.87 / 38.81 | **3.68** / 13.57 / 34.60 |
| Server MSPT (steady): avg / p95 / max | 11.67 / 22.99 / 48.29 | 11.89 / 22.64 / 44.41 |
| Result | **PASS** | **PASS** |
| Session start (55 sessions in one tick, director calls) | 10.1 ms, 0 bots spawned | 12.3 ms, 0 bots spawned |
| All 100 bots live after | 50 ticks | 50 ticks |
| `BotManager.spawn` per tick: avg / p95 / max | 16.4 / 25.4 / 36.5 ms | 13.3 / 16.8 / 53.5 ms |
| `BotManager.spawn` total (adapter / kit / distances) | 820.7 ms (764.2 / 24.4 / 3.0) | 664.1 ms (606.9 / 24.0 / 3.1) |
| Server MSPT over the first 100 ticks: avg / p95 / max | 33.0 / 56.5 / 122.9 | 32.2 / 65.3 / 111.4 |

The single ~0.7–0.8 s tick is gone: the worst spawn tick now costs 37–54 ms of spawning. The first 100 ticks still
average about 32 ms MSPT, as before; most of that is the 55 dummies' own chunk loading/sending (about 2600 chunks),
which the self-test causes, not the bots (bots got 0 chunk packets). Per-spawn cost in this run is 6.6–8.2 ms, a bit
above the earlier 5.3–6.4 ms, because the spawns now overlap the dummies' chunk loading. Admins who need even
smoother starts can set `spawns-per-tick: 1`.
