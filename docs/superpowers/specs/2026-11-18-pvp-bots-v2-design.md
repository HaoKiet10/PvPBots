# PvP Bots v2: Minecraft 26.3, plugin-built arenas, adaptive skill

Status: draft for approval. Builds on the v1 design (`2026-11-12-pvp-bots-design.md`); everything there still
holds unless this document says otherwise.

## 1. Intent

Feedback from the server owner on v1 asked for four things. Three are settled and are this document's scope:

1. **Run on Minecraft 26.3**, the newest release.
2. **Arenas are structures the plugin builds itself.** v1 needs an admin to build an arena by hand and draw a
   WorldGuard region over it; v2 lets the admin place a ready-made arena with one command.
3. **Bots match each player's skill automatically.** v1 has a fixed difficulty per arena; v2 learns each player's
   level quietly and remembers it for next time.

The fourth, **team fights up to 5v5**, is waiting on the owner's answers (who is on each side, what fills empty
slots). v2 only prepares for it: built arenas carry spawn pads for up to 5 per side.

## 2. Goals, non-goals, anti-goals

**Goals**
- The same single jar loads on 1.21.11, 26.1.x, 26.2.x **and 26.3.x**.
- An admin can place, list and remove arenas in-game; removing one puts back exactly the blocks that were there.
- A player's first fight starts at a middle level; within a few fights the trainer is a close match for them, and it
  stays that way as they improve, across restarts.
- Players never see a number, message or sudden change in bot behaviour that gives the adjustment away.

**Non-goals (this version)**
- 5v5 / team matches (waiting on the owner; see §7).
- Any change to boss areas (the user deferred this: "do other thing first when i ask for this").
- Admin-made arena templates from WorldEdit schematics (approach C, possible later).
- Player-visible ratings, ranks or leaderboards.

**Anti-goals** (failures even if it technically works)
- An arena build or removal that destroys terrain or containers that cannot be put back.
- A skill level that swings wildly from one lucky or unlucky fight.
- A bot that visibly "gives up" or freezes mid-fight to let the player win.
- Breaking any v1 behaviour on the three versions already supported.

## 3. Approaches (arena structures)

The user picked **A**.

| | Approach | Trade-off |
|---|---|---|
| **A (picked)** | Arenas generated by code from size settings (width, wall height, materials, pads per side, cover) | Works out of the box, any size from one command, fully testable without a server; arenas look clean but plain |
| B | Built-in WorldEdit `.schem` files | Can look much nicer, but someone must build each in-game; fixed sizes; placeholders until then |
| C | A by default, plus admin-saved WorldEdit schematics as templates | Best of both, but adds spawn-pad marking, validation and admin steps; deferred |

26.3 support and adaptive skill each have one sensible way, described below.

## 4. Minecraft 26.3 support

- New module `adapter-v26_3`, built like `adapter-v26_2` (Java 25, unobfuscated server, no remap) against the
  26.3 Paper dev bundle (`26.3.build.253-stable` was the newest at the M0 spike; the builder uses the newest stable
  26.3 bundle and records it).
- Start as a copy of the 26.2 adapter; fix whatever server internals 26.3 renamed or changed. The M0 spike notes
  (`docs/superpowers/spikes/2026-11-13-m0-results.md`) list every internal the adapters touch: re-check each one.
- `AdapterLoader`: add `^26\.3(\.\d+)?$`; `SUPPORTED` gains `26.3.x`. 26.4+ is still refused with the clear message.
- `plugin`: `runtimeOnly(project(":adapter-v26_3"))`; new `selfTest_26_3` dev server task. WorldEdit 7.4.6 and
  WorldGuard 7.0.19 list 26.3 on Modrinth (same ids as the 26.2 server: WE `YFnqiUlL`, WG `TtfwTyi6`); the builder
  confirms they load.
- Done when: the full self-test (including the new v2 checks) passes on 26.3, and still passes on 1.21.11
  (Java 21 and 25), 26.1.2 and 26.2.

## 5. Plugin-built arenas

### 5.1 What the admin does

```
/pvpbots arena create <name> <duel|squad|team> [confirm]   build an arena centred on where you stand
/pvpbots arena remove <name> [confirm]                     tear it down and restore what was there
/pvpbots arena list                                        name, world, position, size, players inside
```

Permission `pvpbots.admin`. Like `selftest`, `create` and `remove` first print what will happen (size, blocks
affected, any problems) and only act when repeated with `confirm`. Players still need no commands.

### 5.2 Sizes (my call; values live in config so the owner can tune them)

| Preset | Pads per side | Inside floor | Walls | Cover |
|---|---|---|---|---|
| `duel` | 1 | 17 × 17 | 5 high | none |
| `squad` | 3 | 25 × 25 | 5 high | 4 pillars |
| `team` | 5 | 33 × 33 | 5 high | 8 pillars/low walls |

```
  team preset, top view (not to scale)
  ┌───────────────────────────────────────┐
  │ A  A  A  A  A        B  B  B  B  B     │   A/B: spawn pads (marked blocks in the floor)
  │      ▪          ▪          ▪          │   ▪ : cover pillars, 3 high
  │                                       │
  │      ▪          ▪          ▪          │
  └──────────────── [ gap ] ──────────────┘   entrance: 3-wide gap in one wall
```

- Floor one block thick, flush with the block the admin stands on; walls on the outer ring; open roof. Light
  blocks set into the floor in a grid so mobs cannot spawn inside at night.
- Materials per part (floor, wall, light, pad A, pad B, cover) are config entries with defaults (smooth stone,
  stone bricks, sea lantern, blue/red concrete, stone bricks).
- The arena faces the direction the admin is looking: team A's pads on the near side, the entrance behind the
  admin.
- Everything inside the walls, up to wall height + 3, is cleared to air so nothing blocks the fight.

### 5.3 Building safely

- **Checks before `confirm`** (shown in the preview, and re-run on confirm):
  - the whole footprint is inside the world's build height and world border;
  - it does not overlap another PvpBots arena (refuse);
  - it contains no **block entities** (chests, furnaces, signs, spawners, …): refuse and list their positions, so
    no container contents can be lost. The admin moves them and tries again.
  - overlapping an existing WorldGuard region is allowed, with a warning naming the region(s).
- **Snapshot first.** Before changing a block, the plugin saves every block in the affected volume (block data as
  text, palette-compressed, gzipped) to `plugins/PvpBots/arenas/<name>.snapshot`. Removal restores from it.
  The snapshot is written and flushed to disk before the first block changes.
- **Spread over ticks.** Building and restoring change at most `arenas.blocks-per-tick` blocks per tick (default
  4000; a `team` arena is ~10k blocks). Chunks in the footprint are loaded and kept loaded while working. Physics
  updates are off for the placed blocks.
- **Interrupted work** (server stops mid-build or mid-restore): the arena record is saved with status `building`
  or `removing`; on next start the plugin finishes the job from the snapshot (restore if it was removing; finish the
  build if it was building). It never starts a fight in an arena that is not `ready`.
- Entities inside the footprint (dropped items, mobs, armor stands) are left alone; players standing inside during
  a build are teleported onto the finished floor.

### 5.4 Region and registry

- On build, the plugin creates WorldGuard region `pvpbots_<name>` covering the inside of the walls up to wall
  height + 3, priority 10, with `pvpbot-role trainer` (adaptive skill: no `pvpbot-difficulty`), plus `build deny`
  and `pvp allow` so players cannot dig out of or grief the arena. Admins may change flags afterwards with `/rg`;
  the plugin does not reset them.
- Arenas are recorded in `plugins/PvpBots/arenas.yml`: name, world, origin, facing, preset, region id, status,
  snapshot file, and the list of pad positions per team. Pad positions are computed at build time and stored, so
  later 5v5 work reads them instead of re-deriving the layout.
- `remove` ends every trainer session in the arena (bots removed, players get no title), deletes the region,
  restores the snapshot, then deletes the record and snapshot file.
- If the region is deleted by hand, the arena stays in the registry and `arena list` flags it; `remove` still works.

### 5.5 Fights in a built arena

- v1 behaviour otherwise: each player inside gets a personal 1v1 trainer.
- The trainer spawns on the nearest free **team B pad** instead of the v1 "spot near the player" search, so it starts
  across the arena. If every B pad is taken (more players than pads), fall back to the v1 spawn-point search inside
  the region.
- Hand-drawn trainer regions from v1 keep working exactly as before.

## 6. Adaptive skill

### 6.1 Skill as a number

- Each player has a **skill rating** from 0 to 100. The four v1 difficulty profiles become anchor points:
  easy = 0, medium = 33, hard = 67, pro = 100.
- A rating between two anchors gives a profile **blended** between them:
  - number settings (reaction ticks, aim error, turn speed, cooldown min/max, heal-at) are interpolated linearly
    (reaction ticks rounded);
  - on/off and choice settings (crits, w-tap, strafe, shield, totem) **and the kit** take the **lower** anchor's
    value until the rating is within 5 of the higher anchor, so new tricks and gear appear only near the next tier
    (my call: one rule for all of them, so tricks and gear never disagree; at the default 50 that means medium
    tricks and the iron kit);
  - on/off settings, choice settings and the kit are **fixed at the start of the fight** from the starting rating
    (my call: switching any of them mid-fight would be visible). Only the number settings move during a fight.
- The difficulty profiles in `config.yml` keep their meaning and stay tunable; they are now the anchors.

### 6.2 During a fight (quiet adjustment)

- The fight starts from the player's saved rating (50 if they have none, i.e. between medium and hard; my call:
  most players who walk into a PvP arena are not beginners, and the first fight corrects it quickly).
  The kit is chosen from that starting rating.
- Real players **may hurt each other** inside trainer arenas, as in v1 (user's decision), and **every death counts**:
  a player who dies during a fight from any cause (their trainer, another player, lava, falling) loses that round
  for rating purposes (user's decision). Consistently, the in-fight signals below use the player's real health and
  all damage the player takes, whatever its source (my call, following that decision); damage the player deals
  counts only when it hits their own trainer.
- Every `skill.adjust-every-seconds` (default 5) of fighting, the plugin compares how the fight is going:
  - **health lead** (main signal): player health fraction minus bot health fraction, minus `skill.target-lead`
    (default 0.05, so the target is a fight biased slightly in the bot's favour: winnable with effort, not a coin
    flip);
  - **damage share** in the last window (tie-breaker): (player → own trainer) ÷ (that + all damage the player
    took), when anything was traded.
- Decision (my call): if the health lead is beyond the dead zone (default ±0.15), step toward the trailing side.
  Inside the dead zone, step only if the damage share is beyond ±0.3 of even (i.e. below 0.2 or above 0.8) in the
  last window; otherwise leave it. The step is `skill.step` (default 3): the bot's rating for this fight drops when
  the player is behind and rises when the player is ahead. The damage share keeps healing (golden apples, totems)
  from hiding a one-sided window.
- The in-fight rating may move at most `skill.max-shift-per-fight` (default 15) from where it started.
- Changes move only the number settings (reaction ticks, aim error, turn speed, cooldown min/max, heal-at), one
  small step at a time, so the change is invisible: no sudden freeze, no sudden burst. Kit, tricks and totem stay as
  they were at the start (§6.1).

### 6.3 After a fight

- On a result (player wins, bot wins, draw on time limit), the saved rating moves part of the way toward the
  rating the fight ended at, plus a small nudge for the result:
  - `new = old + 0.3 × (fightEnd − old)`, then +4 if the player won, −2 if the bot won, 0 for a draw;
  - clamped to 0..100.
- A player death from any cause during the fight is "bot won" (§6.2).
- Fights that end without a result (player leaves, bot failure, arena removed, `/pvpbots clear`) change nothing.
- Values above are starting points for the feel test; all are config keys under `skill:`.

### 6.4 Storage and scope

- The rating is stored on the player's own persistent data (Bukkit `PersistentDataContainer`, key
  `pvpbots:skill`): no database, survives restarts, moves with the player's save data.
- **One rating per player**, shared by all arenas: skill belongs to the player, not the place.
- Shared server, many players: each player's personal trainer uses that player's own rating.

### 6.5 Fixed difficulty is still possible

- `pvpbot-difficulty` stays. **If set** on a region, that arena is pinned: bots use the fixed profile, nothing is
  measured, and the player's rating is not changed.
- **If unset**, the arena adapts. This changes v1 behaviour: in v1 an unset flag meant medium. Existing hand-drawn
  arenas without the flag become adaptive after the update; ADMIN.md and the release notes must say so.

### 6.6 Allies

Unchanged. Ally squads in boss areas keep their region's fixed difficulty (boss areas are deferred).

## 7. Getting ready for 5v5 (no behaviour yet)

- Built arenas store pads for both teams (§5.4); the `team` preset has 5 per side.
- Ratings are per player, so a later team mode can set enemy bots from the team's average rating.
- Nothing else is built for 5v5 until the owner answers who is on each side and what fills empty slots.

## 8. Testing

- **Unit (no server):**
  - the arena layout generator: footprint, walls, entrance, pad positions per preset and facing;
  - snapshot encode/decode round-trip;
  - profile blending between anchors, including boundaries and discrete-setting thresholds;
  - in-fight adjuster: dead zone, step, max shift, target lead;
  - after-fight update and clamping; no change on no-result endings.
- **In-server self-test**, added to the existing checks, on every supported version including 26.3:
  - A3: build a `team` arena in the temp world over varied terrain, check every block matches the layout and the
    region and flags exist; remove it and check every block matches the original exactly.
  - A4: build refuses a footprint containing a chest; nothing is changed.
  - S1: a trainer fight in an adaptive arena saves a rating on the player; a pinned arena does not.
- **Feel test (manual, added to MANUAL-CHECK.md):** a beginner and a strong player each fight 5 rounds in an
  adaptive arena; fights should feel close by round 3 and the bot should never visibly stall.
